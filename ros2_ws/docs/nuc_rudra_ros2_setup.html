RUDRA robot bring-up

NUC Setup for Ubuntu 26.04 + ROS 2 Lyrical

A fresh-install guide for turning a bare Intel NUC into the RUDRA ROS 2 onboard computer: OS tools, Python, ROS 2, workspace build, shell environment, Teensy access, serial tooling, SSH, and first heartbeat validation.

Outcome

  • Host name: rudra
  • ROS distro: lyrical
  • Workspace: ~/Projects/RUDRA/RUDRAv3/ros2_ws
  • Smoke test: ros2 run rudra_core rudra_alive

1. What This Replaces

The original RUDRA NUC reference was written for Ubuntu 20.04 and ROS 1 Noetic. Its broad intent is still useful: install developer tools, Arduino/Teensy support, serial access, SSH, and the robot workspace. The implementation changes for ROS 2:

Old ROS 1 idea ROS 2 Lyrical version for RUDRA
ros-noetic-desktop-full ros-lyrical-desktop or ros-lyrical-ros-base
catkin, catkin_tools ament packages built with colcon
rosrun, roslaunch ros2 run, ros2 launch
rosserial_arduino Plain serial nodes, swri_serial_util, or micro-ROS for MCU-native ROS 2
devel/setup.bash install/setup.bash
Important: rosserial_arduino was not carried forward as the normal ROS 2 path. For Teensy/Arduino in a ROS 2 robot, decide whether the microcontroller should speak ROS 2 itself through micro-ROS, or whether the NUC should read/write a custom serial protocol and publish ROS 2 topics.

2. Assumptions

Fresh Ubuntu 26.04 User: rudra Host: rudra ROS_DOMAIN_ID=42 Bash shell

This guide assumes the NUC starts from a clean Ubuntu 26.04 install with no ROS workspace, no Python development packages, no serial libraries, and no Arduino/Teensy permissions. Ubuntu usually includes a Python interpreter, but do not rely on a fresh install having pip, venv, headers, build tools, or ROS tooling.

Recommended disk layout

/home/rudra/
  Projects/
    RUDRA/
      RUDRAv3/
        ros2_ws/
          src/
          docs/
          build/     # generated
          install/   # generated
          log/       # generated

Robot network names

  • rudra: robot NUC, onboard computer.
  • aghora: development/control laptop.
  • rudra.local: mDNS name after avahi-daemon is enabled.

3. Install Ubuntu 26.04 on the NUC

  1. Install Ubuntu 26.04 Desktop or Server. Desktop is easier when using RViz, Arduino IDE, and VS Code locally.
  2. Create the user rudra.
  3. Set the computer name to rudra.
  4. Connect to a reliable network before installing ROS packages.
  5. After first boot, open a terminal and run the bootstrap commands below.

Set host name if needed

sudo hostnamectl set-hostname rudra
hostnamectl
cat /etc/hostname

Enable update repositories

sudo apt update
sudo apt upgrade -y
sudo apt install -y software-properties-common
sudo add-apt-repository universe
Reboot after large system upgrades, especially on a brand-new machine. It prevents driver, kernel, and library mismatch problems later in the setup.

5. Install ROS 2 Lyrical

ROS 2 Lyrical provides binary Debian packages for Ubuntu 26.04. For the robot NUC, ros-lyrical-desktop is convenient because it includes RViz and demos. If the NUC must stay lean, use ros-lyrical-ros-base and install visualization tools on the laptop.

Add the official ROS 2 apt source

sudo apt update
sudo apt install -y curl
export ROS_APT_SOURCE_VERSION=$(curl -s https://api.github.com/repos/ros-infrastructure/ros-apt-source/releases/latest | grep -F "tag_name" | awk -F'"' '{print $4}')
curl -L -o /tmp/ros2-apt-source.deb \

if [ -f /opt/ros/lyrical/setup.bash ]; then
    source /opt/ros/lyrical/setup.bash

if [ -f "$RUDRA_WS/install/setup.bash" ]; then

fi

export ROS_DOMAIN_ID=42
export ROS_AUTOMATIC_DISCOVERY_RANGE=SUBNET
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp

# RUDRA workspace helpers
alias gs="git status"

8. Build and Test the RUDRA Workspace

Use rosdep before every first build on a fresh machine. It reads each package's package.xml and asks apt to install the missing system dependencies. 

cd ~/Projects/RUDRA/RUDRAv3/ros2_ws
source /opt/ros/lyrical/setup.bash
rosdep install --from-paths src --ignore-src -r -y
colcon build --symlink-install
source install/setup.bash

Run the RUDRA heartbeat node

ros2 run rudra_core rudra_alive

In another terminal:

source ~/.bashrc
ros2 topic list
ros2 topic echo /rudra/heartbeat

Run tests

cd ~/Projects/RUDRA/RUDRAv3/ros2_ws
colcon test --event-handlers console_direct+
colcon test-result --verbose
When /rudra/heartbeat increments once per second, the NUC has ROS 2, Python, the workspace overlay, and the rudra_core entry point working together.

9. Teensy and Serial Setup

RUDRA hardware talks to the NUC through USB serial devices such as Teensy or Arduino-class controllers. A fresh Linux install needs udev rules and user group membership before non-root processes can open those devices reliably.

User groups

sudo usermod -aG dialout,plugdev rudra
groups rudra

Log out and back in after changing groups.

Install Teensy udev rules

Use the official PJRC rules file when possible. This repository also has a local 00-teensy.rules file at the repo root if you want a pinned copy. 

# Official live copy:
curl -L -o /tmp/00-teensy.rules https://www.pjrc.com/teensy/00-teensy.rules
sudo install -m 0644 /tmp/00-teensy.rules /etc/udev/rules.d/00-teensy.rules

# Repo-pinned copy, if present:
# sudo install -m 0644 ~/Projects/RUDRA/RUDRAv3/00-teensy.rules /etc/udev/rules.d/00-teensy.rules

sudo udevadm control --reload-rules
sudo udevadm trigger

Unplug and reconnect the Teensy after installing the rule.

Install Arduino CLI

sudo apt install -y arduino-cli
arduino-cli version
arduino-cli config init

Add Teensy board support to Arduino tooling

arduino-cli config add board_manager.additional_urls https://www.pjrc.com/teensy/package_teensy_index.json
arduino-cli core update-index
arduino-cli core search teensy

Identify serial devices

lsusb
ls /dev/ttyUSB* /dev/ttyACM* 2>/dev/null
ls -l /dev/serial/by-id 2>/dev/null
dmesg -w

ROS 2 serial options

Option Use when NUC-side packages
Plain serial bridge node The microcontroller sends simple packets, CSV, binary frames, or line-delimited data. pyserial, libserialport-dev, or libcxx-serial-dev
swri_serial_util You want ROS 2 utilities around serial communication. ros-lyrical-swri-serial-util
micro-ROS The Teensy/MCU should participate in ROS 2 using rclc-style APIs. ros-lyrical-rclc, micro-ROS Arduino library, micro-ROS agent if available for the platform.
Do not copy ROS 1 rosrun rosserial_arduino make_libraries.py commands into this ROS 2 setup. They belong to the Noetic workflow and create ROS 1 Arduino libraries.

10. ROS 2 Deep Dive: IMU, Sabertooth, MPU6050, and PS2 Control

The old RUDRA checklist items 9-12 are still important, but each lands in a different place in a ROS 2 robot. The NUC should own ROS 2 topics, transforms, logging, safety gates, and state estimation. The Arduino or Teensy should own tight hardware timing: I2C sensor reads, PS2 receiver polling, PWM/serial timing, and watchdog behavior.

NUC responsibility ROS 2 nodes, sensor_msgs/Imu, sensor_msgs/Joy, cmd_vel, odometry fusion, launch files, parameters, logs, and operator visibility.
Microcontroller responsibility MPU6050 I2C sampling, PS2 controller polling, Sabertooth serial writes, encoder timing, local failsafe, and a compact serial protocol to the NUC.

9. ROS IMU tools in ROS 2

The ROS 1 imu_tools stack exists in ROS 2 and is released for Lyrical. It contains imu_filter_madgwick, imu_complementary_filter, and rviz_imu_plugin. The filters take raw angular velocity and linear acceleration, optionally magnetometer data, and produce an orientation quaternion. 

sudo apt install -y \
  ros-lyrical-imu-tools \
  ros-lyrical-imu-filter-madgwick \
  ros-lyrical-imu-complementary-filter \
  ros-lyrical-rviz-imu-plugin \
  ros-lyrical-robot-localization

Recommended topic contract for RUDRA:

Topic Type Producer Meaning
/rudra/imu/raw sensor_msgs/msg/Imu Serial bridge or micro-ROS agent Raw gyro and accelerometer data. Orientation may be unset.
/rudra/imu/data sensor_msgs/msg/Imu imu_filter_madgwick or complementary filter Filtered IMU with orientation quaternion.
/odometry/filtered nav_msgs/msg/Odometry robot_localization Fused robot state from wheel odom plus IMU.

Run and inspect the filter

source ~/.bashrc
ros2 pkg executables imu_filter_madgwick
ros2 run imu_filter_madgwick imu_filter_madgwick_node \
  --ros-args \
  -r imu/data_raw:=/rudra/imu/raw \
  -r imu/data:=/rudra/imu/data \
  -p use_mag:=false \
  -p publish_tf:=false

In another terminal, verify the message flow: 

ros2 topic hz /rudra/imu/raw
ros2 topic echo /rudra/imu/data --once
ros2 interface show sensor_msgs/msg/Imu
Keep the IMU frame explicit. A good first frame name is imu_link. Mounting direction matters: if the sensor board is rotated relative to base_link, fix that in URDF/static TF or in firmware, not by guessing signs in multiple nodes.

IMU calibration checklist

  • Measure gyro bias while the robot is perfectly still at boot.
  • Publish SI units: radians per second for gyro, meters per second squared for acceleration.
  • Fill covariance values. If unknown, use conservative non-zero diagonal values rather than pretending perfect certainty.
  • Disable magnetometer fusion unless the physical IMU has a calibrated magnetometer and the robot is not near large current loops.
  • Use rviz_imu_plugin or RViz transforms to visually confirm orientation before driving.

10. Sabertooth 2x12 in ROS 2

Sabertooth is not a ROS package; it is a motor driver. In ROS 2, write a NUC-side motor bridge or a microcontroller firmware bridge that converts safe velocity commands into Sabertooth serial commands. For a differential drive robot, the clean ROS graph is: 

/cmd_vel
  -> rudra_base_controller
  -> left/right wheel speed targets
  -> Sabertooth packet serial or simplified serial
  -> motors
  -> encoders
  -> /rudra/wheel_odom
  -> robot_localization

Sabertooth serial modes

Mode When to use ROS 2 implication
Simplified serial One Sabertooth, minimal firmware, single-byte commands. Easy to bring up, but weak addressing and integrity. Good bench test mode.
Packetized serial Robot use, multiple drivers, better command structure. Preferred RUDRA mode. Use address, command, data, and checksum bytes.

Packetized serial uses four bytes: address, command, data, and a 7-bit checksum. The checksum formula from the Sabertooth guide is: 

checksum = (address + command + data) & 0x7f

Python packet helper for a ROS 2 bridge

def sabertooth_packet(address: int, command: int, data: int) -> bytes:
    address &= 0xff
    command &= 0xff
    data &= 0xff
    checksum = (address + command + data) & 0x7f
    return bytes([address, command, data, checksum])

Safety rules for Sabertooth bring-up

  • Start with wheels off the ground.
  • Use a current-limited supply for early tests if possible.
  • Confirm battery chemistry and lithium cutoff DIP switch settings before robot power tests.
  • Use a hardware emergency stop. In packetized serial mode, Sabertooth S2 can be wired as active-low emergency stop.
  • Make the ROS 2 bridge command zero speed if /cmd_vel times out.
  • Log every raw motor command until the sign convention is proven.

11. Arduino MPU6050 libraries in a ROS 2 robot

Jeff Rowberg's I2Cdevlib remains useful on Arduino/Teensy firmware. It is not installed as a ROS 2 package; it belongs in the firmware project. The firmware should read the MPU6050, calibrate it, and send either raw IMU data or a DMP quaternion to the NUC. 

mkdir -p ~/Arduino/libraries
cd ~/Downloads
git clone https://github.com/jrowberg/i2cdevlib.git
cp -r i2cdevlib/Arduino/I2Cdev ~/Arduino/libraries/
cp -r i2cdevlib/Arduino/MPU6050 ~/Arduino/libraries/

Firmware-to-ROS message mapping

MPU6050 value ROS 2 field Notes
Gyro x/y/z angular_velocity Convert to rad/s before publishing.
Accel x/y/z linear_acceleration Convert to m/s^2. At rest, magnitude should be close to 9.81.
DMP quaternion orientation Use only after confirming frame convention and calibration.
Temperature Diagnostic topic Useful for drift debugging, not part of sensor_msgs/Imu.

Serial packet suggestion for IMU

For a custom serial bridge, make the firmware output one complete line per IMU sample. Example CSV shape: 

IMU,stamp_us,gx,gy,gz,ax,ay,az
IMU,18300420,0.001,-0.002,0.003,0.12,-0.05,9.78

The NUC-side ROS 2 Python node reads the line, validates the field count, converts units, fills sensor_msgs/msg/Imu, and publishes /rudra/imu/raw. Keep the parsing strict; malformed sensor packets should increment a diagnostic counter, not silently drive the robot state estimate.

12. Arduino UNO PS2 controller in ROS 2

There are two valid ROS 2 paths for PS2-style control. If the controller appears to Linux as a USB joystick, use ROS 2 joy and teleop_twist_joy directly on the NUC or Aghora. If it is a PS2 wireless receiver wired to Arduino pins, read it in firmware with PS2X_lib, then publish equivalent joystick values to ROS 2 through serial.

Path A: Linux joystick input

sudo apt install -y ros-lyrical-joy ros-lyrical-joy-linux ros-lyrical-teleop-twist-joy
source ~/.bashrc
ros2 run joy joy_enumerate_devices
ros2 run joy joy_node
ros2 topic echo /joy

For direct teleop:

ros2 launch teleop_twist_joy teleop-launch.py joy_config:=ps3

Path B: PS2 receiver wired to Arduino or Teensy

cd ~/Downloads
git clone https://github.com/madsci1016/Arduino-PS2X.git
cp -r Arduino-PS2X/PS2X_lib ~/Arduino/libraries/

Typical PS2 receiver signals are data, command, attention/select, clock, power, and ground. Keep the receiver logic voltage compatible with the microcontroller. Many wireless PS2 receivers are happiest at 3.3 V logic; do not assume a motor-driver board's power pin is a safe logic supply.

Recommended PS2 serial packet

JOY,stamp_us,lx,ly,rx,ry,buttons
JOY,18320100,-0.03,0.91,0.02,-0.01,0x0048

The NUC-side bridge converts that packet to sensor_msgs/msg/Joy. Then RUDRA can use normal ROS 2 tools such as teleop_twist_joy, record joystick input in rosbag2, and replay controller data during debugging.

Bring-up order for the four hardware items

  1. Bring up serial permissions and stable device names under /dev/serial/by-id.
  2. Read MPU6050 on firmware and print calibrated raw values to serial.
  3. Publish /rudra/imu/raw, then run imu_filter_madgwick and inspect /rudra/imu/data.
  4. Read PS2 controller and publish /joy or a serial packet that becomes /joy.
  5. Test Sabertooth serial with motors disconnected or wheels lifted.
  6. Only after signs, scaling, timeout behavior, and e-stop are verified, connect teleop to motor output.
RUDRA's ROS 2 target architecture should be boring in the best way: /joy and autonomous planners produce /cmd_vel; motor bridge owns safety and Sabertooth commands; IMU and wheel odom feed localization; all hardware can be inspected with standard ROS 2 topics.

11. SSH and Networking

The control laptop should reach the NUC over SSH, and ROS 2 discovery should stay on the robot subnet. Keep the same ROS_DOMAIN_ID on every RUDRA machine.

Enable SSH on the NUC

sudo apt install -y openssh-server avahi-daemon
sudo systemctl enable --now ssh
sudo systemctl enable --now avahi-daemon
systemctl status ssh --no-pager
hostname -I

Allow SSH through firewall, if UFW is enabled

sudo ufw status
sudo ufw allow OpenSSH

From Aghora laptop

ssh rudra@rudra.local

Optional laptop-side ~/.ssh/config entry:

Host rudra
    HostName rudra.local
    User rudra
    IdentityFile ~/.ssh/id_ed25519

ROS 2 multi-machine check

On the NUC:

source ~/.bashrc
ros2 run rudra_core rudra_alive

On Aghora, with ROS 2 Lyrical installed and matching environment variables:

export ROS_DOMAIN_ID=42
export ROS_AUTOMATIC_DISCOVERY_RANGE=SUBNET
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
ros2 topic echo /rudra/heartbeat

12. Optional Boot Services

During development, run nodes manually in a terminal. Once a node is stable, create a user-level systemd service so it starts when the NUC boots.

Example: heartbeat service

mkdir -p ~/.config/systemd/user
cat > ~/.config/systemd/user/rudra-alive.service <<'SERVICE'
[Unit]
Description=RUDRA ROS 2 heartbeat node
After=network-online.target

[Service]
Type=simple
ExecStart=/bin/bash -lc 'source /opt/ros/lyrical/setup.bash && source "$HOME/Projects/RUDRA/RUDRAv3/ros2_ws/install/setup.bash" && exec ros2 run rudra_core rudra_alive'
Restart=on-failure
RestartSec=2

[Install]
WantedBy=default.target
SERVICE

systemctl --user daemon-reload
systemctl --user enable --now rudra-alive.service
systemctl --user status rudra-alive.service --no-pager

Keep user services alive after logout

sudo loginctl enable-linger rudra
Only promote a node to a boot service after its serial ports, launch parameters, and emergency-stop behavior are understood. Services restart automatically, which is useful for monitoring nodes and risky for motion nodes if safety logic is incomplete.

13. Troubleshooting

ros2 command not found

source /opt/ros/lyrical/setup.bash
echo 'source /opt/ros/lyrical/setup.bash' >> ~/.bashrc

Workspace package not found

cd ~/Projects/RUDRA/RUDRAv3/ros2_ws
colcon build --symlink-install
source install/setup.bash
ros2 pkg list | grep rudra_core

Serial port permission denied

groups
sudo usermod -aG dialout,plugdev rudra
sudo udevadm control --reload-rules
sudo udevadm trigger

Then log out and back in, and physically reconnect the board.

No /dev/ttyACM0 appears

lsusb
dmesg | tail -n 80
ls -l /dev/serial/by-id 2>/dev/null

Some Teensy sketches only expose USB serial when the firmware is built with a USB serial mode. Also check cable quality: many USB cables provide power but no data lines.

ROS 2 machines cannot see each other

printenv | grep -E 'ROS_DOMAIN_ID|ROS_AUTOMATIC_DISCOVERY_RANGE|RMW_IMPLEMENTATION'
ip addr
ping rudra.local
ros2 multicast receive

In another terminal on the other machine:

ros2 multicast send

apt cannot find ROS packages

. /etc/os-release
echo "$VERSION_ID $VERSION_CODENAME $UBUNTU_CODENAME"
apt-cache policy ros-lyrical-desktop
sudo apt update

Quick health report

source ~/.bashrc
ros2 doctor --report
ros2 pkg prefix rudra_core
ros2 topic list
